What makes VaultKit different

An approval covers one question. Not a table, not a role.

Database roles grant access to a table, indefinitely. VaultKit grants access to a single request: these fields, this time range, for this purpose, until it expires. Change the question and it needs approval again.

A DATABASE ROLE GRANT SELECT ON payments TO agent_reader;
  • Every column, including ones added next month
  • Every row, any time range
  • No record of why the agent asked
  • Valid until someone remembers to revoke it
A VAULTKIT GRANT support-agent may read id, amount, status and a masked customer_email from failed payments in the last 24 hours.
  • Bound to that exact request; a different question needs a new approval
  • Approved by Ada for INC-123, and recorded
  • Masking still applies after approval
  • Expires in 2 hours, and stops working the moment the policy changes
How it works

Configure it from your terminal. Approve from the console.

  1. 1

    Connect a datasource

    VaultKit holds the credential and runs queries next to your data. Agents never see it.

    $ vkit datasource add --id prod_db …
$ vkit scan
  2. 2

    Write policy as code

    Policies live in git, get reviewed like any other change, and deploy pinned to a commit.

    # policies/payments.yaml
match:  { dataset: payments }
action: require_approval
approval:
  approver_role: payments_reviewer
  3. 3

    Point your agents at VaultKit

    Through the MCP server, the Python SDK or the CLI. Approvers act from the console.

    "vaultkit": {
  "command": "vaultkit-mcp",
  "env": { "VAULTKIT_TOKEN": "…" }
}
Every request, four possible answers

Your policy decides before a single row leaves the database.

Allow

Routine questions run straight away. Nothing changes for the developer.

Mask

Sensitive fields come back masked, even after a request is approved.

Require approval

A person in the right group approves the exact request. Nobody approves their own.

Deny

Some data is never returned. And there's no write path at all.

Why IAM isn't enough

IAM answers who may connect. Not what a specific question may return.

Keep your database roles and IAM. VaultKit works at the layer they don't reach: individual requests, individual fields, and why the agent asked.

  • Which fields should this agent see?A table grant includes every column, even one a teammate added last week.
  • Does this request need a person to sign off?Roles are standing permissions. There's no way to approve one query and not the next.
  • Which agent asked, and why?The database sees a service account. VaultKit records which agent asked, with what token, and the purpose it gave.
